Runtime Governance for Autonomous AI Agents

How WitnessOS delivers real-time policy enforcement, immutable audit trails, and cryptographic integrity for agentic AI systems.

Overview

1. Executive Summary

Autonomous AI agents are being deployed into production at an unprecedented rate. These agents browse the web, execute code, call APIs, access databases, and spend money - all without human oversight at the action level. Existing security tools (API gateways, WAFs, IAM policies) were designed for human-initiated requests, not for autonomous agent loops that can make thousands of decisions per minute.

WitnessOS is a runtime governance layer purpose-built for autonomous AI agents. It sits between an agent and its execution environment, intercepting every action the agent attempts and evaluating it against configurable policy before allowing it to proceed. Every decision - allowed, blocked, or flagged - is cryptographically signed and recorded in an immutable audit trail.

WitnessOS is protected by patent pending, covering the methodology for real-time policy evaluation and cryptographic attestation of agent decisions.

Key Design Principle: WitnessOS operates as a transparent middleware layer. Agents connect to it by changing their API endpoint URL - no code changes, no SDK integration, no agent framework fork required.
Why now

2. The Problem: Autonomous Agents Lack Runtime Guardrails

Traditional AI safety focuses on model-level guardrails - prompt filtering, output sanitisation, and content moderation. These are necessary but insufficient for autonomous agents that act in the world.

The critical gap is action-level governance. When an agent decides to execute a shell command, call an API, or access a file, the model-level guardrails have already been bypassed - the agent chose that action. The only place to enforce policy is at the moment the action is executed.

Without runtime governance, organisations face:

  • Uncontrolled tool execution - agents running arbitrary shell commands, database writes, or destructive operations
  • Data exfiltration - agents reading sensitive data and sending it to unapproved third-party APIs
  • Cost runaway - agents trapped in loops that burn through API budgets in minutes
  • Regulatory exposure - no audit trail for agent decisions that impact customers, financial systems, or protected data
  • No human oversight - high-risk actions executed without review, approval, or even awareness

Existing solutions - API gateways, logging middleware, and custom-built policy engines - are retrofits designed for human workflows. They lack the sub-50ms decision latency, the agent-awareness, and the cryptographic audit integrity that autonomous systems require.

Architecture

3. Architecture Overview

WitnessOS is deployed as a lightweight gateway between AI agents and their execution targets. The architecture consists of three core components:

3.1 The Gateway

The gateway is a stateless HTTP/HTTPS proxy that intercepts every agent action in real-time. Agents connect by configuring their API base URL to point at the WitnessOS endpoint. The gateway:

  • Accepts incoming action requests from any agent framework (OpenAI, Anthropic, LangChain, CrewAI, custom)
  • Parses the action into a structured decision record: agent_id, action_type, target, payload_signature, timestamp
  • Evaluates the action against the active policy set in under 50 milliseconds
  • Returns a decision: ALLOW, BLOCK, FLAG, or ESCALATE

3.2 The Policy Engine

The policy engine evaluates every action against a configurable rule set defined as YAML. Policies are built from three primitive constructs: 

rules:
- name: block-destructive-commands
  match:
    action_type: shell_exec
    payload_contains: ["rm -rf", "DROP TABLE", "shutdown"]
  action: BLOCK

- name: flag-high-value-transactions
  match:
    action_type: api_call
    target_domain: "*"
    payload_value_gt: 1000
  action: FLAG

- name: require-approval-external-egress
  match:
    action_type: api_call
    target_domain: "!*.internal.corp"
  action: ESCALATE

Policies support: allow lists, block lists, regex pattern matching, rate limiting, token budgets, time-based constraints, and role-based escalation rules. Policies are evaluated in order - first match wins - with a default-deny fallback.

3.3 The Audit Store

Every decision produces an audit record that is cryptographically signed and written to the audit store. The store is append-only and tamper-evident. Each record contains: 

{
  "sequence": 104729,
  "agent_id": "agent-prod-03",
  "timestamp": "2026-07-04T14:32:17.893Z",
  "action_hash": "sha256:ab12...ef34",
  "decision": "BLOCK",
  "policy_rule": "block-destructive-commands",
  "signature": "ecdsa:v2:7f9c...2b1a",
  "prev_signature": "ecdsa:v2:3a8b...c4d2"
}

The prev_signature field chains each record to its predecessor, creating a hash-linked chain that makes retroactive tampering detectable. Any modification to a historical record breaks the chain and is immediately identifiable.

Policy enforcement

4. Policy Enforcement Model

WitnessOS implements a four-tier decision model that gives organisations fine-grained control over agent behaviour:

Tier 1: ALLOW

The action is permitted and logged. Used for routine, low-risk operations that fall within clearly defined safe parameters - reading approved data sources, calling whitelisted APIs, executing safe commands.

Tier 2: BLOCK

The action is rejected with an explanatory error returned to the agent. The agent receives structured feedback: {"error": "POLICY_BLOCK", "rule": "block-destructive-commands", "reason": "Shell command contains destructive pattern"}. This allows agents to self-correct and choose alternative actions.

Tier 3: FLAG

The action is permitted but flagged for human review. A notification is sent via the configured channel (Slack, Teams, email, webhook). A human can retroactively approve or reject the action - though the action has already occurred, the flag creates an accountability trail. Flagged actions are automatically summarised in periodic review reports.

Tier 4: ESCALATE

The action is paused pending human approval. The agent receives a pending response and must wait. The human receives a decision request via the configured channel with full context - agent identity, action details, risk assessment. If no response is received within a configurable timeout, the action defaults to BLOCK.

Operational Consideration: Escalation timeout defaults to 5 minutes. For latency-sensitive workflows, organisations can configure a shorter timeout with a conditional allow-after-timeout policy.
Evidence integrity

5. Audit Trail Integrity & Cryptographic Signing

The audit trail is the foundation of WitnessOS's value proposition. Every decision - not just blocks, but every allow - is recorded with full cryptographic integrity.

5.1 Hash-Chain Construction

Audit records are linked in a hash chain using SHA-256. Each record's prev_signature field contains the ECDSA signature of the preceding record, creating a tamper-evident sequence: 

Record[N] = {
  ...data...,
  "prev_signature": signature(N-1)
}

signature(N) = ECDSA_SIGN(
  SHA256( Record[N] ),
  private_key
)

This means:

  • Changing any field in any historical record breaks that record's signature
  • The broken signature no longer matches what's stored in the next record's prev_signature
  • Re-signing the altered record requires the private key, which is protected by hardware-backed key storage
  • The chain can be verified end-to-end by any party with the public verification key

5.2 Key Management

Signing keys are generated and stored per-tenant. For cloud deployments, keys are stored in hardware security module (HSM) backed key vaults. For on-premises deployments, keys are generated on the customer's infrastructure and never leave it. Key rotation is supported without breaking chain integrity - each record includes the key version used for signing.

5.3 Independent Verification

The audit store exposes a verification endpoint that accepts any audit record range and returns a verification status. Third parties - auditors, regulators, customers - can independently verify the integrity of the audit trail without accessing the signing keys. The public verification key is published to a tenant-specific endpoint.

Security model

6. Security Model & Data Isolation

6.1 Data in Transit

All communication between agents, the WitnessOS gateway, and execution targets uses TLS 1.3 with strong cipher suites (TLS_AES_256_GCM_SHA384). Certificate pinning is supported for organisations with strict transport security requirements.

6.2 Data at Rest

Audit records, policy configurations, and agent metadata are encrypted at rest using AES-256-GCM. Each tenant's encryption keys are isolated. For on-premises deployments, customers manage their own encryption keys. The gateway itself stores no agent payloads or responses - only the metadata necessary for policy evaluation and audit.

Critical Design Decision: WitnessOS never stores agent prompts, LLM responses, or intermediate reasoning traces. Only action metadata - what the agent attempted, what policy was applied, and the decision - is recorded. This minimises data exposure and simplifies compliance.

6.3 Authentication & Authorisation

Agents authenticate to the gateway using API keys with role-based access control. Each agent is associated with a set of policies, rate limits, and budget constraints. API keys support rotation, revocation, and granular scoping. The gateway supports mTLS for agent-to-gateway authentication in private deployments.

6.4 Tenant Isolation

In multi-tenant cloud deployments, each tenant operates in a logically isolated context with dedicated encryption keys, policy namespace, and audit store. Row-level security is enforced at the database layer. For organisations requiring physical isolation, enterprise deployments offer dedicated single-tenant infrastructure.

6.5 Zero Data Egress

The gateway can be configured to operate in zero-egress mode, where no data - audit records, policy decisions, or telemetry - leaves the customer's network. In this mode, the gateway operates fully disconnected from WitnessOS cloud services. Audit records are stored locally and can be replicated to the customer's SIEM or data lake.

Compliance

8. Compliance & Regulatory Framework

WitnessOS is designed to help organisations meet compliance requirements across multiple regulatory frameworks.

8.1 Australian Privacy Principles (APP)

The audit trail generated by WitnessOS supports APP compliance by providing a tamper-evident record of all agent actions that process personal information. Organisations subject to the Privacy Act 1988 (Cth) can use WitnessOS audit trails to demonstrate:

  • APP 1 - Open and transparent management: Documented policies governing agent behaviour, with an auditable record of enforcement.
  • APP 11 - Security of personal information: Proven controls preventing unauthorised access, modification, or disclosure by AI agents.
  • APP 12 - Access to personal information: Complete audit trail showing what personal information agents accessed and why.

8.2 SOC 2

For organisations subject to SOC 2 requirements, WitnessOS provides:

  • Security: Default-deny policy engine, mTLS agent authentication, and cryptographic audit integrity.
  • Availability: Stateless gateway architecture supporting horizontal scaling and zero-downtime deployments.
  • Confidentiality: Data isolation per tenant, encryption at rest and in transit, zero-egress deployment option.

8.3 GDPR

WitnessOS supports GDPR compliance by providing:

  • Data processing records via the audit trail for controller obligations
  • Data minimisation through configurable audit retention policies
  • Right to erasure via audit trail purge capabilities
  • Data Processing Agreement (DPA) available for Enterprise customers

8.4 Industry-Specific Compliance

WitnessOS is designed to be deployment-flexible so it can operate within regulated environments including healthcare (HIPAA, My Health Records), financial services (APRA CPS 234), and government (ISM, IRAP). On-premises deployment with customer-managed keys is the recommended model for regulated industries.
